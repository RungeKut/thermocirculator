# 07. Диагностика известных проблем

Актуально на 16.09.2026. Каждая запись: симптом → причина → проверка → решение.

## П-01. Сборка обрывается: «ARM-Compiler ... is not available» — устранено

**Симптом**

```
*** Target 'STM32L071CBT6' uses ARM-Compiler 'Default Compiler Version 5'
    which is not available.
*** Rebuild aborted.
```

Затрагивает **оба** ST-проекта: у них в `.uvprojx` стоит `<uAC6>0</uAC6>`.

**Причина**

Проекты требуют Arm Compiler 5, а в установленной MDK 5.39 его нет —
каталог `C:\Keil_v5\ARM\ARMCC` отсутствует, остался только `ARMCLANG`
(Arm Compiler 6.21). Компилятор пропал при переустановке MDK.

**Это не ошибка в коде.** До переустановки обе прошивки собирались
успешно: L072 — 02.03.2025 (0 ошибок, 0 предупреждений), L071 — январь 2026
(слинкована прошивка 26.90 КБ).

**Проверка**

```bash
ls /c/Keil_v5/ARM/          # есть ли ARMCC рядом с ARMCLANG
head -1 <проект>/MDK-ARM/<таргет>/*.map   # чем собиралось в прошлый раз
```

**Решение** (выполнено 17.09.2026)

Компилятор извлечён из дистрибутива MDK 5.36 — последней версии, где он
есть, — и положен в `C:\Keil_v5\ARM\ARMCC`. Устанавливать 5.36 не нужно:
её дистрибутив распаковывается 7-Zip как обычный архив.

**Одних файлов недостаточно.** MDK 5.39 не ищет AC5 сам; пока в
`C:\Keil_v5\TOOLS.INI` нет строки регистрации, ошибка остаётся прежней:

```
ARMCCPATH1=".\ARMCC" ("V5.06 update 7 (build 960)")
```

Оба шага делает `tools\install-ac5.ps1`. Проверка — сборка L072 должна дать
**27 796 байт**.

Альтернатива на будущее — перевод на ArmClang или GCC, см.
[adr/0001-toolchain.md](adr/0001-toolchain.md).

## П-02. L071 собирается, но показывает 0 °C и не греет

**Симптом**

Прошивка линкуется без ошибок, дисплей работает, но все температуры равны
нулю, нагрев не включается.

**Причина**

При перегенерации проекта в CubeMX потеряна конфигурация АЦП: остались
только каналы `ADC_CHANNEL_0/1/2`, а `ADC_CHANNEL_TEMPSENSOR` и
`ADC_CHANNEL_VREFINT` исчезли (в `.ioc` L072 они присутствуют как
`VP_ADC_TempSens_Input` и `VP_ADC_Vref_Input`, в `.ioc` L071 их нет).

Код выбирает канал напрямую через `ADC1->CHSELR`, поэтому каналы 16 и 17
выберутся. Но биты включения внутренних источников (`ADC->CCR`: `TSEN`,
`VREFEN`) выставляет `HAL_ADC_ConfigChannel()` при инициализации — и теперь
их не выставляет никто. Дальше по цепочке:

- `sense[4]` (VREFINT) = 0, а он служит **делителем**;
- `senseAdcRef = (sense[4]/4095)*3.3` = 0;
- все три температуры = `calc_temperature(...) * senseAdcRef/12` = **0**;
- `senseTempMCU` = деление на ноль.

**Проверка**

```bash
grep -c "ADC_CHANNEL_TEMPSENSOR\|ADC_CHANNEL_VREFINT" STM32L071CBT6/Core/Src/adc.c
# 0 — конфигурация потеряна; 2 — на месте
```

В отладчике: `sense[4]` должен быть около 1500…1700 при исправном VREFINT.

**Решение**

Вернуть в CubeMX и перегенерировать:

| Что | Значение | Где потеряно |
|---|---|---|
| Канал `TEMPSENSOR` | включить | `Core/Src/adc.c` |
| Канал `VREFINT` | включить | `Core/Src/adc.c` |
| `ClockPrescaler` | `SYNC_PCLK_DIV4` | стало `DIV2` |
| `SamplingTime` | `12CYCLES_5` — проверено на железе | стало 1.5 такта |
| Прерывание `RTC_IRQn` + `sAlarm` | включить | `Core/Src/rtc.c`, `stm32l0xx_it.c` |
| PB12, PB13, PB6, PB7 | вход с подтяжкой вниз | `Core/Src/gpio.c` |
| PB15 | вход | `Core/Src/gpio.c` |
| `HAL_RCCEx_EnableLSECSS()` | вызвать | `Core/Src/main.c` |

Время выборки 1.5 такта мало для NTC через 10 кОм: ёмкость устройства
выборки-хранения не успевает зарядиться, показания будут занижены и шумны.
Рабочее значение для этой схемы — **12.5 такта**, подтверждено измерениями
на L072.

## П-03. Правки в `Core/` исчезают после CubeMX

**Симптом**

После перегенерации проект снова ведёт себя как до исправлений.

**Причина**

CubeMX сохраняет только то, что находится между маркерами
`/* USER CODE BEGIN ... */` и `/* USER CODE END ... */`. Всё остальное
перезаписывается из `.ioc`.

В проекте был след этой проблемы: в `.ioc` L072 стояло
`ADC_SAMPLETIME_160CYCLES_5`, а в сгенерированном `Core/Src/adc.c` —
`ADC_SAMPLETIME_12CYCLES_5`, вне блоков `USER CODE`. Значение 12.5 такта
было подобрано **на железе**, а не в CubeMX, и правка легла поверх
сгенерированного кода — то есть любая перегенерация её потеряла бы.

**Устранено 17.09.2026:** `.ioc` приведён в соответствие с проверенным на
железе кодом (`ADC.SamplingTime=ADC_SAMPLETIME_12CYCLES_5`). Источником
истины остаётся `.ioc`, но теперь он описывает работающую конфигурацию.

**Проверка**

Перед перегенерацией:

```bash
grep -n "SamplingTime" <таргет>/Core/Src/adc.c <таргет>/*.ioc
```

Значения должны совпадать. Если нет — в коде есть ручная правка, которая
будет потеряна.

**Решение**

Правило: **настройки периферии меняются только через `.ioc`.** Если значение
в CubeMX недоступно — правка идёт в блок `USER CODE`, а не поверх
сгенерированного кода. См. [08-rules.md](08-rules.md).

## П-04. uVision не видит целевое устройство

**Симптом**

Устройство не выбирается в настройках таргета, либо не разрешаются исходники
SPL в проекте GD32.

**Причина**

Не установлены пакеты поддержки устройств.

Для GD32 это критично: проект `keil/` подключает SPL через механизм RTE из
`keil/RTE/Device/GD32E103C8/`, и эти файлы приходят из пакета.

> **Ловушка: пакеты лежат не там, где кажется.** MDK 5.39 держит их в
> профиле пользователя — `%LOCALAPPDATA%\Arm\Packs\`, а **не** в
> `C:\Keil_v5\ARM\PACK\`. Последний остался от старых версий, содержит
> только `.Download` и `.Web`, и распаковка пакета туда **не даёт ничего**:
> uVision продолжает сообщать, что пакет не установлен. Проверено
> 17.09.2026 — время потеряно именно на этом.

**Проверка**

```bash
ls ~/AppData/Local/Arm/Packs/
```

Должны быть каталоги `Keil/STM32L0xx_DFP/2.2.0` и
`GigaDevice/GD32E10x_DFP/1.3.0`.

**Решение**

Установить пакеты из офлайн-комплекта — [03-environment.md](03-environment.md),
шаг 3. Версии зафиксированы в `.uvprojx`, ставить нужно именно их.

> `UV4.exe -pack <файл>` в версии 5.39 **молча ничего не делает** и
> возвращает 0. Установка без графического интерфейса — только распаковкой
> вручную, см. шаг 3.

## П-05. Отладчик не соединяется с GD32

**Симптом**

ST-Link, перепрошитый в J-Link, не видит GD32E103.

**Причина**

Зафиксированный опыт проекта: связка с GigaDevice не заработала.
Перепрошивка китайского ST-Link в J-Link сама по себе удалась (сначала
накатывается обычная прошивка STM32 + VCP), но с GD32 соединения получить
не удалось.

**Решение**

Использовать отдельный J-Link. Артефакты прошлых попыток —
`keil/JLinkLog.txt`, `keil/JLinkSettings.ini`.

## П-06. На GD32 не выводится на дисплей после инициализации таймера

**Симптом**

Дисплей и индикатор ведут себя непредсказуемо после вызова `TIM1_Init()`.

**Причина**

`TIM1_Init()` в `keil/Core/Src/tim.c` переводит в режим альтернативной
функции пины **PA15, PB3, PB10, PB11** — то есть `SPEAKER`, `DISP_DB3`,
`DISP_DB2` и `LED_R`. Для отладки ШИМ это допустимо, но конфликтует с
дисплеем.

**Решение**

Оставить под таймер только пин `SPEAKER`; остальные вернуть в режим выхода.
Задача входит в портирование, см. [06-porting.md](06-porting.md).

## П-07. GD32 не собирается: не задана частота кварца

**Симптом**

```
gd32e10x.h(62): error: "Please select the target board type used in your
                        application (in gd32e10x.h file)"
system_gd32e10x.c(801): error: use of undeclared identifier 'HXTAL_VALUE'
```

**Причина**

`gd32e10x.h` из пакета требует, чтобы частота внешнего кварца была задана
явно. Он выводит её из макроса платы (`GD32E103V_EVAL` — 8 МГц,
`GD32E103R_START` — 25 МГц) либо из прямого определения `HXTAL_VALUE`.
В проекте `keil/gd32e103c8t6.uvprojx` поле Define **пустое**, поэтому
ни один вариант не срабатывает.

Кроме того, RTE-копия `keil/RTE/Device/GD32E103C8/system_gd32e10x.c`
выбирает `__SYSTEM_CLOCK_120M_PLL_HXTAL` (120 МГц), а комментарий в
`keil/Core/Src/adc.c` исходит из 72 МГц. Эти два места между собой
не согласованы.

**Почему раньше собиралось**

Старый лог сборки указывает на пути вида
`C:/Users/bspch/AppData/Local/Arm/Packs/...` — то есть **проект собирался
на другой машине под другим пользователем**. Отсюда же файлы `*.uvguix.bspch`.
Скорее всего там был отредактирован сам `gd32e10x.h` внутри установленного
пакета: именно это и предлагает сделать текст ошибки. Такая правка живёт
вне контроля версий и не переносится — классическое «работает у меня».

**Решение**

Задать частоту в **настройках проекта**, а не правкой пакета:
`Options for Target → C/C++ → Define`, например `HXTAL_VALUE=8000000`
плюс `HXTAL_VALUE_8M` (последний выбирает ветку настройки PLL в
`system_gd32e10x.c`).

Конкретное значение зависит от кварца на плате и **подлежит уточнению**.
Заодно следует согласовать выбранную частоту системной шины: 120 МГц в
`system_gd32e10x.c` против 72 МГц в комментариях к АЦП.

## П-08. Инсталлятор STM32CubeMX не запускается

**Симптомы**

Одно из двух окон:

```
This application requires a Java Runtime Environment 1.8.0_45 (64-bit)
Unsufficient rights to install, please try as administrator
```

Либо, при запуске из консоли, инсталлятор завершается с кодом 1 и
**не выводит ничего**.

**Причина**

Две независимые проверки на старте инсталлятора.

1. **Права.** Без прав администратора инсталлятор прекращает работу.
   В автоматическом режиме — молча, с кодом 1.

2. **Java.** Лаунчер ищет JRE в реестре
   `HKLM\SOFTWARE\JavaSoft\Java Runtime Environment`. На машине нет
   зарегистрированной Java вообще: единственная JRE лежит внутри
   STM32CubeIDE (`C:\ST\STM32CubeIDE_1.3.0\STM32CubeIDE\jre`), но в реестре
   не значится, поэтому лаунчер её не видит. Строка `1.8.0_45` присутствует
   прямо в теле инсталлятора.

**Проверка**

```powershell
Test-Path 'HKLM:\SOFTWARE\JavaSoft\Java Runtime Environment'
```

**Решение**

Оба препятствия снимает `tools\install-cubemx.ps1`, запущенный **от имени
администратора**: он ставит Temurin JRE 8 с компонентом
`FeatureOracleJavaSoft` (создаёт нужные ключи реестра), затем три версии
CubeMX в автоматическом режиме.

> Обычной установки JRE недостаточно, если не выбран компонент
> `FeatureOracleJavaSoft` — без него ключи `JavaSoft` не создаются и
> лаунчер по-прежнему не находит Java.

> **Третье препятствие: сценарий автоустановки.** Даже с правами и Java
> инсталлятор прекращает работу без единого сообщения, если сценарий
> IzPack неточен. Сочинять его по описанию бесполезно: у панели `readme`
> обязателен атрибут `id`, а панель ярлыков требует пяти дочерних
> элементов. Рабочие сценарии берутся у самого мастера — он предлагает
> сохранить их на последнем шаге установки, и они лежат в комплекте как
> `tools/installers/cubemx/auto-install-<версия>.xml`.

> Для версии 6.0.1 есть обходной путь без установки JRE: её инсталлятор —
> обычный JAR, и запускается любой Java 8, например той, что внутри
> STM32CubeIDE: `java.exe -jar SetupSTM32CubeMX-6.0.1.exe auto-install-6.0.1.xml`.
> У 6.2.0 и 6.4.0 это не работает: они собраны как native-инсталляторы.

## Диагностические приёмы

**Чем собиралась прошивка в прошлый раз**

```bash
head -1 <проект>/MDK-ARM/<таргет>/*.map
```

**Полный ли линк** — есть ли в сборке прикладные модули:

```bash
grep -c "UserInterfaceExecuter\|TempMeasExecuter\|HeaterExecuter" *.map
```

**Размер прошивки** — сверить с эталоном в [04-build-and-flash.md](04-build-and-flash.md):

```bash
grep -i "Total ROM Size" *.map
```

**Расхождение кода и `.ioc`** — см. П-03.
