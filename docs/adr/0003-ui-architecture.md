# ADR-0003. Архитектура интерфейса: дерево меню и два языка

- **Дата:** 16.09.2026
- **Статус:** предложено
- **Контекст:** [09-requirements.md](../09-requirements.md)

## Проблема

Новое ТЗ требует развитой системы меню: настройки, выбор языка, калибровка
двух датчиков, выбор типа датчика, четыре способа настройки ПИД, пороги
кулера, скорость нагрева, просмотр датчиков уровня, журнал ошибок,
многоступенчатые программы.

Текущая реализация это не выдерживает. В
[`user_interface.c`](../../STM32L072CBT6/User/Src/user_interface.c) экраны —
это `switch` по номеру, реакция на кнопки — вложенный `switch` по состоянию
и коду кнопки, строки зашиты литералами прямо в вызовах вывода. Каждый новый
пункт меню требует правок в трёх местах, а число сочетаний «состояние ×
экран × кнопка» растёт быстрее, чем его можно удержать в голове.

Добавление второго языка при таком устройстве невозможно: строки не собраны
в одном месте.

## Решение

Разделить **описание** интерфейса и **механику** его работы.

### 1. Декларативное дерево меню

Меню — константная таблица во флеше, а не код. Добавление пункта становится
добавлением строки в таблицу.

```c
typedef enum {
    NODE_SUBMENU,   // переход в подменю
    NODE_ENUM,      // выбор из списка (язык, тип датчика, метод автонастройки)
    NODE_NUMBER,    // числовое значение с шагом и границами
    NODE_ACTION,    // запуск действия (автонастройка, очистка журнала)
    NODE_VIEW,      // живые показания, только чтение (датчики, уровень)
    NODE_LIST,      // прокручиваемый список (журнал ошибок, программы)
} node_kind_t;

typedef struct menu_node {
    str_id_t              title;      // идентификатор строки, не текст
    node_kind_t           kind;
    const struct menu_node *children; // для NODE_SUBMENU
    uint8_t               child_count;
    const void           *binding;    // что читать и куда писать
} menu_node_t;
```

Ключевое: `title` — **идентификатор строки, а не текст**. Это то, что
делает возможным второй язык.

### 2. Обобщённые редакторы

На каждый вид узла — один редактор, общий для всех пунктов этого вида.
Редактор числа умеет границы, шаг и ускорение при удержании; редактор
перечисления умеет листать варианты. Новый пункт меню не требует нового
кода вывода и обработки кнопок.

### 3. Таблица строк

```c
typedef enum { LANG_RU, LANG_EN, LANG_COUNT } lang_t;

extern const char *const strings[LANG_COUNT][STR_COUNT];
```

- Строки в UTF-8 — драйвер дисплея уже принимает UTF-8 и переводит в коды
  знакогенератора.
- В коде интерфейса **нет строковых литералов**. Проверяется грепом.
- Отсутствующий перевод — ошибка сборки, а не пустая строка на экране.

### 4. Длина строки считается в символах

`LCD_PrintActiveString()` сейчас берёт длину через `strlen()`, то есть в
**байтах**. В UTF-8 кириллический символ занимает 2 байта, поэтому для
русского текста центрирование и длина прокрутки вычисляются неверно.

Сейчас это не проявляется: интерфейс почти целиком английский. С появлением
русского языка дефект становится систематическим, поэтому подсчёт длины
переводится на символы.

### 5. Навигация

Единая для всего дерева, пять существующих кнопок:

| Кнопка | Действие |
|---|---|
| Menu | Войти в пункт / подтвердить и перейти к следующему |
| Left / Right | Перемещение по пунктам, изменение значения |
| Start | Подтвердить, запустить действие |
| Stop | Назад, отменить правку |

Поведение одинаково на любой глубине — пользователю не нужно помнить, где
он находится.

### 6. Вывод на дисплей 8×2

Подтверждено 17.09.2026: дисплей **8×2**, восемь знакомест. Это самое
жёсткое ограничение всего интерфейса, и компоновка строится вокруг него.

**Правило разделения строк:**

| Строка | Содержимое | Поведение |
|---|---|---|
| Верхняя | Название пункта — длинное, переводимое | Прокручивается |
| Нижняя | Значение — короткое, обычно числовое | Помещается целиком |

Обоснование: значения почти всегда укладываются в восемь знакомест
(`60.0°C`, `РУС`, `12:34:00`, `E-10`, `3988`), а названия на русском —
почти никогда. Поэтому прокручивается **только верхняя строка**, а нижняя
остаётся статичной и читаемой. Глаз пользователя держится за значение, пока
название проезжает.

**Следствия для таблицы строк:**

- Для каждого пункта хранится полное название; сокращать его не нужно —
  прокрутка справляется.
- Там, где значение всё же длиннее восьми знакомест (например, тип датчика
  `10k B3988`), прокручивается и нижняя строка, но такие случаи следует
  сводить к минимуму подбором формулировок.
- Журнал ошибок ложится на эту схему естественно: верхняя строка
  прокручивает подробный текст неисправности, нижняя показывает код и время
  (`E-10 14:23`). Именно это делает подробные формулировки из каталога
  неисправностей осмысленными на таком экране.

Существующий механизм бегущей строки (`LCD_PrintActiveString`,
`RunLineExecuter`) переиспользуется как есть — после исправления подсчёта
длины в символах (пункт 4).

## Последствия

**Положительные**

- Пункт меню добавляется строкой в таблицу, а не тремя правками в коде.
- Второй язык становится возможным в принципе.
- Дерево меню лежит во флеше, а не в ОЗУ — существенно при 20 КБ ОЗУ.
- Механика меню не зависит от платформы: это часть `app/`, общая для
  всех трёх МК.

**Отрицательные**

- Переработка `user_interface.c` — самый крупный по объёму пункт ТЗ.
  Существующий автомат режимов работы (`stateCurrent`, `stateRun`) при этом
  сохраняется: меняется оболочка интерфейса, а не логика прибора.
- Прирост прошивки около 8 КБ (строки двух языков и дерево меню) —
  учтено в бюджете памяти в [09-requirements.md](../09-requirements.md).

**Порядок**

Делается **после** выделения `app/` и `port/` ([ADR-0002](0002-shared-codebase.md)),
на эталонном L072, где есть рабочая прошивка для сверки поведения.
