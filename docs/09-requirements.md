# 09. Техническое задание на переработку

Записано 16.09.2026 со слов владельца проекта. Статус: **черновик, два
вопроса открыты** — см. раздел «Открытые вопросы».

## Рамки

**Печатная плата не меняется.** Новых интерфейсов, новой памяти и новых
датчиков не появляется. Все изменения — программные, на существующем железе:
три NTC-входа, два датчика уровня, пять кнопок, дисплей, ТЭН, два мотора,
кулер, пищалка.

Это важное следствие для архитектуры: контракт `ports.h` из
[ADR-0002](adr/0002-shared-codebase.md) остаётся почти без изменений —
добавляются только ШИМ кулера, доступ к RTC и сторожевой таймер.

**Суть задачи — переработка интерфейса.** Требуется развитая система меню,
которую текущая структура кода не выдерживает: сейчас это плоский автомат на
`switch` с жёстко зашитыми строками в
[`user_interface.c`](../STM32L072CBT6/User/Src/user_interface.c).

## Функциональные требования

### Ф-01. Меню настроек

Отдельный раздел меню, доступный из режима останова. Древовидная структура
с разделами, перечисленными ниже.

### Ф-02. Язык интерфейса: русский и английский

- Выбор языка в меню настроек, сохраняется в энергонезависимой памяти.
- Все строки интерфейса переводимы; в коде не остаётся литералов.
- Интерфейс должен вмещать слова и аббревиатуры **разной длины**: русские
  слова длиннее английских, а видимая ширина дисплея мала. Механизм —
  уже реализованная бегущая строка.

> **Требует исправления:** `LCD_PrintActiveString()` вычисляет длину через
> `strlen()`, то есть считает **байты**. Строки в проекте — UTF-8, где
> кириллический символ занимает 2 байта. Для русского текста центрирование
> и длина прокрутки считаются неверно. Сейчас это не проявляется, потому что
> интерфейс почти целиком английский. Для двуязычного интерфейса длина должна
> считаться в символах, а не в байтах.

Драйвер дисплея кириллицу поддерживает: `LCD_PrintString()` принимает UTF-8
и переводит в коды знакогенератора, символ `°` выводится из CGRAM.

### Ф-03. Калибровка датчиков температуры

- **Два подключаемых датчика** (разъёмы X7 и X8) калибруются пользователем
  через меню.
- **Датчик радиатора и внутренний датчик МК** калибруются в коде и
  пользователю недоступны. Для них — **только меню просмотра показаний**.
- Калибровочные коэффициенты хранятся в энергонезависимой памяти
  раздельно для каждого датчика.
- Метод: не менее двух точек (смещение и наклон). Одной точки недостаточно
  для требования Н-01.

### Ф-04. Выбор типа датчика из списка

Вместо таблицы, заносимой вручную, — **список типов датчиков с готовыми
коэффициентами**, как в промышленных приборах. Выбор типа для каждого из
двух подключаемых датчиков.

**Решено 17.09.2026: речь о разных типах NTC-термисторов** (вопрос В-01
закрыт). Термопары не рассматриваются — плата не меняется.

Тип датчика описывается парой «сопротивление при 25 °C» и «коэффициент B»,
либо тремя коэффициентами Стейнхарта — Харта для большей точности.

Вместо хранения таблицы на каждый тип температура вычисляется:

```
R_ntc = RA * code / (4096 - code)        // RA — резистор делителя
T     = 1 / (1/T25 + ln(R_ntc/R25) / B)  // уравнение B
```

Термистор включён нижним плечом делителя: с ростом температуры сопротивление
и код АЦП падают, что соответствует существующей таблице (2223 при 20 °C,
351 при 100 °C).

Расчёт выполняется раз в секунду на датчик — логарифм в программной
плавающей точке на Cortex-M0+ это допускает. Существующая таблица остаётся
как один из типов списка и как эталон для сверки.

> **Ограничение, следующее из неизменности платы.** Резистор делителя
> RA = 10 кОм (по расчёту существующей таблицы; подлежит сверке со схемой).
> Он подобран под термистор 10 кОм и обеспечивает лучшую линейность
> в рабочем диапазоне. Датчики с сильно отличающимся R25 (например, 100 кОм)
> уводят рабочую точку к краю шкалы АЦП, и требование Н-01 для них может
> не выполняться. Список типов следует ограничить теми, что работают с
> RA = 10 кОм в диапазоне 20…100 °C, а для остальных — предупреждать о
> снижении точности.

> **Точность модели.** Уравнение B даёт расхождение с реальной кривой
> порядка ±0.5 °C на диапазоне 20…100 °C, что на границе требования Н-01.
> Для встроенных типов предпочтительны коэффициенты Стейнхарта — Харта
> (±0.1 °C); двухточечная калибровка Ф-03 компенсирует остаток.

### Ф-05. Настройка ПИД-регулятора нагревателя

Раздел меню с вариантами:

1. **Ручной ввод** коэффициентов Kp, Ki, Kd.
2. **Автоматический подбор по реакции на ступень** (Циглер — Никольс,
   разомкнутый контур): подаётся ступень мощности, измеряются запаздывание
   и постоянная времени.
3. **Автоматический подбор релейным методом** (Аустрём — Хеглунд): вводятся
   автоколебания вокруг уставки, из периода и амплитуды вычисляются
   критические параметры. Основной метод для тепловых объектов.
4. **Автоматический подбор по Коэну — Куну** — из тех же измерений, что и
   вариант 2; лучше работает при большом запаздывании.

Требования к автонастройке:

- процесс прерывается кнопкой Stop в любой момент;
- ограничения по температуре и времени соблюдаются во время настройки;
- результат показывается перед сохранением, сохранение подтверждается;
- при несхождении — ошибка E-27, прежние коэффициенты сохраняются.

Одновременно устраняется отсутствие защиты от интегрального насыщения —
см. [05-firmware.md](05-firmware.md).

### Ф-06. Скорость приближения к заданной температуре

Задаваемое ограничение скорости нагрева (°C/мин). Реализуется движущейся
уставкой: ПИД получает не конечную температуру, а плавно нарастающую.
Значение 0 — ограничение выключено, нагрев на полной мощности.

> Требует решения: как ограничение сочетается с существующим уходом в паузу
> за 5 °C до уставки и сигналом готовности (см. [05-firmware.md](05-firmware.md)).

### Ф-07. Управление кулером по температуре радиатора

Линейная зависимость скважности ШИМ от температуры радиатора, задаётся
двумя точками:

- `T0` — температура, при которой ШИМ = 0 %;
- `T100` — температура, при которой ШИМ = 100 %.

Между ними — линейная интерполяция, за пределами — насыщение.

**Проверено по даташитам 17.09.2026. Аппаратный ШИМ на PA8 есть не везде:**

| МК | Альтернативные функции PA8 | Канал таймера |
|---|---|---|
| GD32E103 | USART0_CK, **TIMER0_CH0**, CK_OUT0, VCORE, USBFS_SOF, CTC_SYNC | **есть** |
| STM32L072 | MCO, USB_CRS_SYNC, EVENTOUT, USART1_CK, I2C3_SCL | **нет** |
| STM32L071 | то же без USB | **нет** |

Источники: `stm32l072cz.pdf`, таблица 17 (стр. 53); `GD32E103xx_Datasheet_Rev1.14.pdf`
(стр. 26). Для сравнения, у соседнего PA7 каналы таймеров есть (TIM3_CH2,
TIM22_CH2) — но перевести кулер на другой вывод нельзя, плата не меняется.

**Решение: программный ШИМ от свободного таймера по прерыванию.** На
STM32L071/L072 занят только TIM2 (звук), свободны TIM6, TIM7, TIM21, TIM22.
Один из них настраивается так, чтобы по переполнению выставлять PA8, а по
совпадению — сбрасывать. При частоте ШИМ около 100 Гц это 200 прерываний в
секунду с очень коротким обработчиком — нагрузка пренебрежимая даже для
Cortex-M0+ на 32 МГц.

Такой ШИМ не нагружает основной цикл и не имеет недостатка медленного
программного ШИМ нагревателя (период 1 с), от которого вентилятор
пульсировал бы и мог не запуститься.

На GD32 порт использует аппаратный канал TIMER0_CH0 — различие прячется
за `port_cooler_pwm()` и прикладного кода не касается.

> **Минимальная рабочая скважность.** Двухпроводные вентиляторы постоянного
> тока обычно не стартуют ниже 25…35 % и могут заглохнуть на малой
> скважности. Линейный закон поэтому задаётся не от нуля: ниже `T0`
> вентилятор выключен полностью, а при включении сразу подаётся минимальная
> рабочая скважность, либо кратковременный импульс 100 % для страгивания.
> Конкретные значения подбираются на живом вентиляторе.

### Ф-11. Настройка громкости звукового сигнала

Регулировка громкости пьезоизлучателя через меню настроек, значение
сохраняется в энергонезависимой памяти.

**Как это реализуется на неизменной плате.** Излучатель подключён к PA15 и
питается ШИМ от таймера. Сейчас скважность жёстко равна 50 %:

```c
void SetSoundFreq(float f){
    uint16_t reg = round(32000000/f);
    TIM2->ARR = reg;
    TIM2->CCR1 = reg/2;      // ровно половина — громкость не регулируется
}
```

Пьезоизлучатель — ёмкостная нагрузка. При коротких импульсах элемент не
успевает зарядиться до полного напряжения, размах на нём падает, и звук
становится тише. Поэтому громкость регулируется **скважностью**: `CCR1`
становится долей от `ARR`, а не половиной. Диапазон — примерно от 1 % до
50 %; выше 50 % громкость не растёт, форма сигнала лишь зеркалится.

Требования:

- шкала громкости в меню (например, 0…10), где **0 — полное отключение**;
- значение применяется ко всем сигналам: готовность, авария, завершение,
  сохранение;
- при изменении громкости в меню воспроизводится пробный сигнал, чтобы
  выбор был слышен.

> **Зависимость громкости нелинейна** и меняет тембр: чем уже импульс, тем
> звук не только тише, но и «суше». Равномерной шкалы из этого не получится,
> шаги подбираются на слух.

**Нижний предел громкости для аварийных сигналов — обязателен**
(решено 17.09.2026). Настройка громкости действует на все сигналы, но для
аварийных не опускается ниже заданного минимума, включая положение «0».
Распространяется на **все аварийные случаи** из каталога неисправностей, а
не только на перегрев и отсутствие воды.

### Ф-11.1. Коррекция громкости по частоте

Излучатель — **TDK PS1740P02E**: пьезоизлучатель внешнего возбуждения,
диаметр 17 мм, **резонансная частота 4.0 кГц**. Подробнее —
[02-hardware.md](02-hardware.md).

Ниже резонанса отдача пьезоэлемента падает круто: элемент работает в области,
где излучение ограничено собственной жёсткостью, и звуковое давление быстро
снижается с уменьшением частоты. Отсюда два следствия для текущих мелодий:

- все используемые ноты (523…1865 Гц) лежат **существенно ниже резонанса**,
  то есть излучатель работает в самой неэффективной своей области;
- разброс громкости между нотами велик: ЛЯ# аварийного сигнала (1865 Гц)
  заметно громче ДО сигнала готовности (523 Гц) при одинаковой скважности.

**Рекомендация: перенести сигналы вверх, ближе к 4 кГц.** Транспонирование
существующих мелодий на две октавы сохраняет музыкальные интервалы и
переводит их в эффективную область:

| Нота | Сейчас | На две октавы выше | `ARR` при 32 МГц |
|---|---|---|---|
| ДО | 523.25 Гц | 2093 Гц | 15 288 |
| МИ | 659.26 Гц | 2637 Гц | 12 135 |
| СОЛЬ | 783.99 Гц | 3136 Гц | 10 204 |
| ДО (верхняя) | 1046.50 Гц | 4186 Гц | 7 644 |

Верхняя ДО попадает практически в резонанс. Аварийный сигнал имеет смысл
задать прямо на 4.0 кГц — это даёт максимальную громкость при той же
мощности, что особенно важно с учётом обязательного нижнего предела.

Побочная выгода: в эффективной области **у регулировки громкости появляется
реальный запас вниз**. Сейчас, работая далеко ниже резонанса, излучатель и
так тихий, и уменьшать скважность почти некуда.

**Механизм коррекции.** Поправочный коэффициент к скважности как функция
частоты, таблицей с линейной интерполяцией:

```c
typedef struct { uint16_t hz; uint8_t gain_pct; } spl_point_t;
```

Важное ограничение: скважность ограничена сверху 50 %, поэтому коррекция
может только **ослаблять** громкие ноты до уровня самой тихой, а не усиливать
тихие. Если оставить ноты в текущем низкочастотном диапазоне, выравнивание
сделает все сигналы тихими. Это второй аргумент за транспонирование.

> **Таблица заполняется по факту, а не по справочнику.** Значения следует
> взять из АЧХ в даташите PS1740P02E либо, что точнее, **измерить в готовом
> корпусе**: закрытый корпус с выходным отверстием образует резонатор
> Гельмгольца со своей собственной резонансной частотой, которая может
> заметно сместить итоговую характеристику относительно паспортной. Пока
> измерения нет, коэффициенты задаются единичными — коррекция отключена.
> Даташит излучателя подлежит добавлению в `tools/datasheets/`.

### Ф-12. Проигрыватель звука не должен блокировать основной цикл

Обнаружено при разборе Ф-11; исправляется вместе с ним.

Сейчас `Sound()` проигрывает мелодии цепочкой `HAL_Delay()`, полностью
останавливая основной цикл:

| Сигнал | Время блокировки |
|---|---|
| Завершение (`C`) | 30 × 4 × 20 мс = **2400 мс** |
| Авария (`A`) | 4 × 2 × 300 мс = **2400 мс** |
| Готовность (`H`) | 4 × 200 мс = 800 мс |
| Сохранение (`S`) | 4 × 100 мс = 400 мс |

Всё это время **не выполняются** измерение температуры, пересчёт ПИД,
опрос кнопок и опрос датчиков уровня. То есть во время аварийного сигнала
прибор на две с лишним секунды перестаёт следить за уровнем воды и
регулировать нагрев.

Требование: проигрыватель переводится на неблокирующую схему — партитура
как таблица «частота, длительность», продвижение по ней из основного цикла
по таймеру, как у остальных исполнителей.

> **Про нижнюю границу частоты — это осознанное решение, а не недосмотр.**
> `SetSoundFreq()` записывает `32000000/f` в 16-битный регистр, из-за чего
> частоты ниже 488 Гц неработоспособны. Настройки таймера выбраны именно так
> сознательно: излучатель ниже ~500 Гц всё равно ничего не воспроизводит,
> поэтому диапазон ограничен сверху разрядностью регистра ровно там, где он
> заканчивается физически. Предделитель не нужен.
>
> При переносе сигналов вверх по Ф-11.1 запас по регистру только растёт
> (`ARR` = 7644 на 4186 Гц против 61155 на 523 Гц), а на GD32 с тактовой
> 72 МГц делитель пересчитывается в порте.

## Нефункциональные требования

### Н-01. Точность измерения температуры не хуже 1 %

Для рабочей точки 60 °C это ±0.6 °C.

Что требуется в цепи измерения:

| Фактор | Сейчас | Нужно |
|---|---|---|
| Разрядность АЦП | 12 бит, одна выборка на канал в секунду | Передискретизация с усреднением (16–64 выборки) |
| Время выборки | 12.5 такта на L072 | Не менее 12.5; на L071 сейчас 1.5 — ошибка |
| Ratiometric-коррекция по `VREFINT` | есть | сохранить |
| Шаг таблицы | 2 °C с линейной интерполяцией | достаточно (погрешность < 0.05 °C) |
| Допуск резистора делителя | неизвестен | компенсируется калибровкой Ф-03 |
| Саморазогрев термистора | ~0.27 мВт | в норме (предел 1 мВт) |

Двухточечная калибровка (Ф-03) — основной механизм достижения 1 %:
она снимает разброс номиналов резистора и самого датчика.

### Н-02. Совместимость с тремя таргетами

Все требования реализуются в общей части `app/` и работают одинаково на
STM32L072, STM32L071 и GD32E103. Различия допустимы только в `port/`.

### Н-03. Сохранность настроек

Все настройки (язык, калибровки, типы датчиков, коэффициенты ПИД, пороги
кулера, скорость нагрева, программы) хранятся в энергонезависимой памяти с
контрольной суммой. При несовпадении — загрузка значений по умолчанию и
запись ошибки E-23.

## Бюджет памяти

### Хранилище настроек и программ

Сейчас: одна страница 128 байт по адресу `0x0801F800`, 32 значения по 32 бита —
занята полностью 16 программами по два значения.

Предложение: выделить **8 КБ** под настройки, программы и журнал ошибок.

| МК | Флеш | Прошивка | 8 КБ хранилища | Остаток |
|---|---|---|---|---|
| STM32L072CBT6 | 128 КБ | ~42 КБ (оценка) | 8 КБ | ~78 КБ |
| STM32L071CBT6 | 128 КБ | ~42 КБ | 8 КБ | ~78 КБ |
| GD32E103C8T6 | **64 КБ** | ~42 КБ | 8 КБ | ~14 КБ |

При шаге профиля 8 байт (температура + длительность) 8 КБ вмещают около
1000 точек. Ориентир: **32 программы по 16 точек** — это 512 точек, около
4 КБ, с запасом на заголовки и журнал.

Ограничение GD32: страница стирания **1 КБ** против 128 байт у STM32L0.
Простой цикл «прочитать — стереть — записать» на 1 КБ дорог и изнашивает
флеш. Нужна журнальная запись с переносом, скрытая за `port_nvs_*`.

### Объём прошивки — следствие для тулчейна

Оценка прироста: строки двух языков (~150 строк × 2 × ~20 байт ≈ 6 КБ),
дерево меню (~2 КБ), три метода автонастройки (~2 КБ), журнал и диагностика
(~2 КБ). Итого прошивка вырастает примерно с 27 до **~42 КБ**.

> **Это окончательно закрывает вопрос по бесплатной редакции Keil:**
> MDK-Lite ограничена 32 КБ, новая прошивка в неё не поместится.
> Аргумент за переход на GCC из [ADR-0001](adr/0001-toolchain.md)
> становится решающим. На GD32E103C8T6 (64 КБ) запас останется, но
> небольшой — около 14 КБ.

## Влияние на архитектуру

Хорошая новость: новой периферии нет, поэтому контракт `ports.h` из
[ADR-0002](adr/0002-shared-codebase.md) почти не меняется. Добавляются:

```c
void     port_cooler_pwm(uint8_t percent);   // Ф-07
uint32_t port_rtc_now(void);                 // метки времени в журнале, Ф-09
void     port_rtc_set(uint32_t seconds);
void     port_wdt_kick(void);                // E-20, E-25
port_reset_cause_t port_reset_cause(void);   // E-20, E-21
```

Контракт растёт с 15 до ~20 функций — по-прежнему немного.

Основная работа — не в портах, а в переработке `app/`: декларативное дерево
меню, таблица строк с языками, слой калибровки датчиков, журнал ошибок,
диспетчер диагностики. Архитектура интерфейса вынесена в
[ADR-0003](adr/0003-ui-architecture.md).

Подтверждается порядок работ из [01-overview.md](01-overview.md): выделение
`app/` **до** доделки GD32. Объём изменений по этому ТЗ таков, что
портировать сначала старую структуру означает выбросить работу целиком.

## Закрытые вопросы

### В-01. Тип датчиков — решено 17.09.2026

Речь о **разных типах NTC-термисторов**, не о термопарах. Плата не меняется,
доработка аналоговой части не требуется. Реализация — Ф-04.

Для справки, почему термопары исключены: термопара выдаёт около 40 мкВ/°C,
а младший разряд 12-битного АЦП при опоре 3.3 В равен 0.806 мВ — это
**около 20 °C на единицу кода**. Потребовались бы усилитель и компенсация
холодного спая, то есть изменение платы.

### В-02. Ширина дисплея — решено 17.09.2026

Дисплей **8×2 (0802)**. Восемь знакомест, две строки.

Это жёсткое ограничение компоновки: на русском языке восемь знакомест — это
одно короткое слово. Правила компоновки вынесены в
[ADR-0003](adr/0003-ui-architecture.md).
